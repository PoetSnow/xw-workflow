# Agent 通用底座

供核实。这是底座的边界，不是某个业务的实现计划。代码还没按这份文档改。

底座不包含具体业务。业务方只通过下面四个扩展点接入。换一个行业，不改底座工程。

Agent 仍是独立宿主，不进 Web 的 `src/Modules`。

## 底座负责什么

底座只提供能力，不解释业务 JSON。

| 能力 | 底座保证 |
| --- | --- |
| 知识检索 | 按调用方给出的资料集入库、检索，并返回可引用的命中 |
| 模型 | 按 Profile 调用模型，屏蔽地址、密钥和协议差异 |
| 工具 | 按能力说明执行一次调用。来源可以是 HTTP、进程内处理器，以后也可以是 MCP |
| 对话 | 多轮会话里做检索、规划、授权、执行、回复 |
| 作业 | 接收一次异步请求，按种类分发给已登记的处理器，再把结果送回 |

Web 或其他系统要驱动 Agent 时走作业，不把 Agent 嵌进自己的进程。人在对话里用 Agent 时走对话。两条入口最后都调用知识检索、模型和工具。业务名词只出现在作业的 `kind`、工具的编码，以及处理器自己的 JSON 里。

## 四个扩展点

业务包只依赖契约，不依赖向量库、HTTP 客户端、模型客户端和对话循环。

### 资料集是不透明编号

调用方自己规定编号的含义。底座不解释它是项目、客户还是制度库，也不为任何业务建主数据。

入库、删除、检索都带资料集编号。检索的编号列表为空时直接拒绝，不扫全库。

命中只含引用所需的字段：资料集、文档 Id、切块 Id、标题、来源、片段、分数。底座不在命中上增加业务字段。

现在的 `domain` 列就是这个编号。存储查询已经能按它过滤。`VectorKnowledgeRetriever` 调用时传了 `domain: null`，调试接口也没传范围。底座要补上的是「必须带范围」，不是新的业务表。

对话里的知识工具同样带范围。关闭向量或 Embedding 时返回空结果，不回退词法检索。

### 工具是一份说明加一种执行

规划器只看说明：编码、何时使用、参数、权限、风险。它不看 HTTP 路径，也不看模型名字。

执行绑定三选一，由底座完成调用：

- `http`：方法、路径、参数模板
- `handler`：业务包里的一个类
- `mcp`：以后由底座的 MCP 客户端发现并投影成同一份说明

权限、确认、超时在底座里，对三种绑定一样。业务包不因为换了模型或换了 MCP 而改分支。

### 作业是一个信封

同步对话解决不了「别的系统叫我做一件事，做完送回去」。这件事用作业，不用把对话编排暴露给调用方。

请求只有这些字段：

- `jobId`：调用方生成，结果原样带回
- `kind`：处理器名称，由业务包登记
- `corpusIds`：资料集编号。这次不用检索则为空列表
- `input`：业务包自己定义的 JSON
- `replyTo`：结果送回的路由

结果只有这些字段：

- `jobId`
- `status`：`succeeded` 或 `failed`
- `hits`：这次用到的引用。没有检索则为空
- `output`：业务包自己定义的 JSON
- `error`

底座按 `kind` 找到处理器并调用。处理器可以使用知识检索、模型和工具。底座不解析 `input` 和 `output`。

传输与作业分开。进程内可以直接调用作业运行时。出进程时用现有 CAP：Infrastructure 负责订阅和按 `replyTo` 回发。不另做消息中间件。调用方是 Web 还是别的系统，底座不关心。

### 对话里的停顿是协议，不是业务步骤

需要用户补充、选择或确认时，业务包实现待办处理器：根据 `kind` 和用户这句回复，给出下一步是调用工具、继续追问，还是结束。

底座只保存待办种类和步骤，并把下一句路由到对应处理器。文案、槽位名和结束条件都在处理器里。

## 依赖

```
Host → Infrastructure → Contracts
业务包 → Contracts

对话运行时 → 知识检索、模型、工具、作业分发
消息适配 → 作业运行时
调试 API → 知识检索
```

业务包不引用 Infrastructure。Infrastructure 不引用业务包。Host 点名登记业务包，不在启动时扫描程序集猜有哪些业务。

这一阶段不建立业务包项目。契约里先放资料集、命中、工具说明、作业信封、处理器接口。检索实现放进 Infrastructure。Host 提供带资料集参数的调试检索。对话循环仍留在现有工程，新的检索入口不经过编排器。

现有业务不是底座的一部分，开工时不保证它们继续可用，也不迁进扩展点。挡路的业务代码删除，不修复。细则见 `docs/agent/agent-kickoff.md`。

## 一个新业务怎么接

1. 约定自己的资料集编号，把文档入库。
2. 需要模型调用外部能力时，登记工具说明和绑定。
3. 需要被别的系统异步调用时，登记一个 `kind` 和处理器。处理器读 `input`，可调用检索，把本业务的 JSON 写入 `output`。
4. 需要多轮确认时，登记一个待办处理器。
5. 在 Host 的模块目录里加上这个包。

多数业务只做第 1 步和第 2 步，包里是 JSON。出现处理器时才在业务包里加类。只有这条业务要单独交付时，才把它拆成独立项目。

## 明确不做

- 底座不出现具体业务的类型、表和文案。
- 不为某条业务流程设计专用作业种类。种类由业务包登记。
- 不把调用方的主数据同步进 Agent。
- 不让业务包依赖向量库、CAP 客户端或模型 SDK。
- 不按业务域拆底座项目。
- 不改知识库表。资料集使用现有 `domain` 列。
- 不在代码里写 `INSERT` / `CREATE TABLE`。

## 核实

- 底座是知识检索、模型、工具、对话、作业。业务只登记说明和处理器。
- 资料集编号对底座不透明。检索不带编号就拒绝，不扫全库。
- 作业的 `input` / `output` 由业务包定义。底座只路由 `kind`。
- 对话和消息是两种入口，下面是同一套检索、模型和工具。
- 采购、库存、以及任何举例里的业务流程，都不是这一阶段要实现的处理器。
