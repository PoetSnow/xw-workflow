一、分布式锁（库存扣减 + 设备绑定）
简历依据
“结合分布式锁控制并发访问，保障库存扣减和订单创建的数据准确性” + “设备弱网环境下的数据同步、失败重试及数据幂等”

引导句（什么时候说）
聊到库存模块时顺带一句：

“多门店库存各自独立，秒杀并发扣减的时候，用Redis分布式锁控制了一下，防止超卖。”

核心回答（对方问“怎么实现的”时）
实现方式：

用Redis的 SETNX + 过期时间，Key = stock_lock:{门店ID}:{商品ID}

Value存当前请求的唯一ID（比如订单号），释放时先GET判断是不是自己的锁再DEL

库存扣减用Lua脚本把“判断库存是否充足”和“扣减库存”两个操作打包，保证原子性

设了超时时间防止死锁（比如3秒）

解决的问题：

防止超卖：两个线程同时扣最后一件库存，只有一个能成功

防止重复绑定：同一设备被两个门店同时扫码，只有一个能绑定成功

深挖追问链
Q1：“为什么要用Lua脚本？”

“因为判断库存和扣减是两个独立的Redis命令。高并发下可能A线程判断有库存，还没扣，B线程进来扣完了，A再扣就超卖了。Lua脚本把这两个操作打包，Redis执行时不会被其他命令打断，保证原子性。”

Q2：“释放锁的时候为什么要先判断Value？”

“防止误删别人的锁。比如A线程的锁超时了（3秒），锁自动释放，B线程拿到锁。这时候A线程执行完了，如果直接DEL Key，会把B的锁删掉。所以释放时先GET，判断Value是不是自己的请求ID，是才删，不是就跳过。”

Q3：“锁超时时间怎么设？业务执行超过了怎么办？”

“超时时间按业务评估，正常库存扣减<100ms，我设了3秒留够余量。极端情况（比如DB慢查询）超时了，做了续命机制——后台线程每1秒检查一次，业务没结束就重置过期时间。续命本身也有风险，如果业务卡死会一直续命，所以续命设置了总时长上限（比如30秒），超了就不续了，让锁自动释放。”

Q4：“Redis单节点挂了怎么办？”

“降级到数据库乐观锁。库存表加一个version字段，更新时UPDATE inventory SET quantity=quantity-1, version=version+1 WHERE product_id=@pid AND store_id=@sid AND version=@oldVersion，影响行数为0说明被别人改了，重试或返回失败。性能比Redis差，但能保证数据不错。”

二、事务一致性（支付单 + 下单 + 库存）→ 提到CAP工具
简历依据
“任务状态管理和失败重试，保证业务数据的最终一致” + “跨系统业务流程”

引导句（什么时候说）
聊到支付或下单流程时顺带一句：

“支付涉及生成单子、调渠道、回调通知好几个环节，跨系统了，用CAP框架做的最终一致性。”

核心回答（对方问“怎么做的”时）
CAP是什么：

.NET开源的分布式事务框架，内置了本地消息表 + MQ自动发送 + 自动重试 + 幂等消费

我用的CAP + RabbitMQ，事务内发消息，CAP自动管理消息表的写入和发送

具体用法：

支付接口里，在同一个数据库事务中：插入支付单 + capBus.PublishAsync()

事务提交后，CAP自动把消息发到RabbitMQ（失败自动重试）

消费者用 [CapSubscribe] 接收消息，处理渠道调用/回调通知

失败自动重试，全部失败进死信队列

解决的问题：

支付单生成和消息发送要么都成功要么都失败（同一个DB事务）

跨系统调用失败不影响本地数据（先落库，后通知）

最终一致性，允许短暂不一致，但最终一定达成

深挖追问链
Q1：“CAP的本地消息表是怎么工作的？”

“CAP在业务库里自动建了两张表：cap.published（已发布消息）和cap.received（已接收消息）。业务代码里用BeginTransaction()把业务操作和Publish包在同一个事务里，事务提交后CAP后台线程从cap.published表扫描待发送消息，发到RabbitMQ，发送成功更新状态。接收端收到消息先插cap.received做幂等，再去执行业务逻辑。”

Q2：“如果CAP发消息失败了怎么办？”

“CAP后台线程会持续扫描重试，默认是每分钟扫描一次，重试次数和间隔都可以配置。我设的是重试5次，间隔递增（1分钟、5分钟、15分钟、30分钟、1小时）。5次全失败，消息状态标记为Failed，进死信队列，系统告警人工介入。”

Q3：“CAP的幂等是怎么做的？”

“每条消息有唯一ID，CAP收到消息后先查cap.received表，如果ID已存在就直接ACK跳过，不重复执行业务逻辑。这样即使RabbitMQ重复投递，业务也不会重复处理。”

Q4：“为什么不用TCC或分布式事务框架？”

“支付场景链路长（调渠道可能要几秒），用TCC会长时间占用资源，太重了。而且下游渠道不支持TCC协议。我们接受短暂的不一致（用户看到‘处理中’），只要最终一致就行。CAP+对账这套方案够用、稳定、易于理解。”

Q5：“CAP工具本身有没有出过问题？”

“遇到过两次：一次是CAP表所在DB连接超时，导致消息发不出去，加了重试和告警解决。一次是消费者代码有Bug，消息一直失败，CAP一直重试，队列积压，修复Bug后消费恢复。总的来说CAP挺稳定的，重试和幂等做好了，基本不用操心。”

三、数据缓存（订单查询 + 配置信息）
简历依据
“通过Redis缓存优化热点数据访问”

引导句（什么时候说）
聊到优化时顺带一句：

“订单查询和商户配置读多写少，用Redis缓存扛一下，DB压力小很多。”

核心回答（对方问“怎么做的”时）
缓存什么：

商户费率配置、商品信息、门店配置（读多写少，变更不频繁）

订单的快照信息（减少连表查询）

读写策略：

读：先查Redis → 没有查DB → 回填Redis

写：更新DB → 删除Redis缓存（下次读重新加载）

解决的问题：

减少DB查询压力，热点数据访问速度从几十毫秒降到几毫秒

深挖追问链
Q1：“为什么更新时不更新缓存，而是删除？”

“更新缓存有并发问题——两个线程同时改，后改的覆盖先改的，数据就乱了。删除更简单安全，下次读的时候从DB加载最新的，保证最终一致。代价就是删除后下一次查询慢一点，但对于读多写少的场景完全可以接受。”

Q2：“Redis挂了怎么办？”

“做了降级：加了一层本地缓存（Caffeine），优先读本地，没有就读Redis，都没有才查DB。Redis挂了本地还能撑1-2分钟，这段时间足够运维介入恢复。另外设置了熔断，Redis连续失败几次后自动跳过，直接查DB，业务不中断。”

Q3：“缓存和DB数据不一致怎么办？”

“业务上允许最多5分钟的不一致窗口。后台修改配置时主动删缓存，保证下次读加载最新数据。核心数据还做了延迟双删——更新DB后立即删缓存，1秒后再删一次。防止A线程删缓存后，B线程读到旧数据又回填，第二次删除把这个脏数据清掉。”

Q4：“缓存雪崩怎么防？”

“过期时间加随机偏移，比如5分钟±30秒，避免大量Key同时失效。核心配置永不过期，靠主动删缓存来更新。”

四、消息队列异步（AI分析 + 设备上报）
简历依据
“通过异步任务机制提升系统稳定性” + “消息队列实现设备数据采集、任务分发、算法处理、结果生成的异步处理流程”

引导句（什么时候说）
聊到AI模块时顺带一句：

“AI分析一张图片要十几秒，同步等用户受不了，用MQ异步做，设备上报完就返回。”

核心回答（对方问“怎么做的”时）
流程：

设备上报数据 → 生成AI任务（状态=待处理）→ 发MQ → 立即返回

后台消费者收到消息 → 调AI服务 → 存结果 → 更新任务状态

前端轮询或WebSocket推送结果

为什么用MQ：

异步解耦：设备上报不依赖AI服务的可用性

削峰填谷：AI服务处理慢，MQ缓冲，不会压垮

深挖追问链
Q1：“AI分析失败了怎么处理？”

“消费者里做重试，失败后消息不ACK，重新入队。重试3次还失败，状态标记为失败，发告警。AI服务修好后可以手动重跑。不影响设备上报，用户看到的是‘分析失败，请重新尝试’。”

Q2：“消费者处理到一半服务重启了，消息会不会丢？”

“不会。用的手动ACK，处理完才发ACK。没发ACK就重启，RabbitMQ会把消息重新投递给其他消费者。结合业务幂等（任务ID去重），不会重复处理。”

Q3：“为什么不用HTTP同步调AI？”

“同步调的问题是：AI分析耗时5-30秒，HTTP连接早超时了。而且AI服务不稳定，直接影响设备上报的成功率。加MQ后设备上报只写DB+发MQ，耗时<50ms，AI服务挂了设备端也感知不到。”
